# Память проекта KobraS1BotWiki

## Назначение

KobraS1BotWiki — Telegram-бот поддержки групп по 3D-принтерам Anycubic. Бот ищет ответы в вики, хранит рабочие данные в одной SQLite-базе и предоставляет веб-панель и Mini App.

## Проверенный стек

- Python 3.12 на локальной Windows-машине; CI использует Python 3.11.
- Зависимости приложения фиксируются в `requirements.lock`.
- Полный набор проверок запускается через pytest; Ruff и coverage выполняются отдельно.

## Модерация групп

- В `app/bot/handlers/_cmd_moderation.py` реализованы reply-команды `/ban`, `/unban`, `/kick`, `/mute`, `/unmute`, `/warn`, `/unwarn`, `/warnings`, `/clearwarns`, `/del`, `/pin`, `/unpin`.
- Исполнительные команды принимаются только в группе или супергруппе от её владельца/администратора. Перед изменением Telegram-состояния бот проверяет собственное право `can_restrict_members`, `can_delete_messages` или `can_pin_messages`.
- Предупреждения не применяют автоматическое наказание и ограничены по объёму; данные хранятся в namespace `moderation` общей базы `data/chat.sqlite3`.
- Журнал админских действий и известные активные баны/муты хранятся в namespace `admin_activity` той же базы; события Telegram дополняются непосредственной записью успешных команд бота. События, инициированные самим ботом, обновляют active-state, но не дублируют журнал. В Mini App админский вход остаётся привязан к `PANEL_ADMIN_CHAT_ID`, а вкладка статистики позволяет выбирать только чаты из `ALLOWED_CHAT_IDS` (по умолчанию `-1002295062981`, если он настроен).

## Команды Telegram и дневная статистика

- `app/bot/command_menu.py` при старте обновляет встроенное меню Telegram через `set_my_commands`: участники групп видят `/start` и `/help`, администраторы — также служебные и модерационные команды; списки локализованы для `ru`/`en`.
- `/stats` не должен удалять команду или ответ. Обработчик `cmd_stats` не вызывает `schedule_delete_slash_command_and_reply`; это покрыто тестами для личного чата и групповой темы.
- `app/bot/daily_summary.py` содержит 50 базовых начал и 50 концовок, расширенных до 500 вариантов каждого типа. Формулировки используют совместимое с `группе`, `этой теме` и `чату` «по …», а формы количества сообщений выбираются автоматически (`1 сообщение`, `2 сообщения`, `5 сообщений`, `21 сообщение`).
- `app/bot/daily_stats.py` ежедневно в 08:00 по Europe/Kaliningrad отправляет сводку предыдущего дня в каждый чат из `ALLOWED_CHAT_IDS`; в форумах — в General (`message_thread_id=1`), в обычных группах — обычным сообщением. Для каждого чата используются отдельные `get_daily_stats`/`get_daily_top_topics` с его `chat_id`. При отсутствии списка используется `PANEL_ADMIN_CHAT_ID`.
- Последний production-релиз этих изменений: `1b838fa` от 2026-09-17; сервис `kobras1botwiki.service` проверен активным под `anycubicwikibot`.

## Единая история и AI-темы — актуально на 2026-09-22

- Каноническое хранилище истории — единая SQLite-база `data/chat.sqlite3`. Telegram и Mini App используют один файл; строки Telegram разделяются по `chat_id` и `topic_id`, а Mini App работает только со строками без `chat_id`.
- Входящие Telegram-сообщения сохраняются до фильтров, включая медиа и сообщения без текста. Ответы поддержки бота тоже сохраняются с источником и `reply_to_id`.
- Статистика читается из SQLite; старые JSON-агрегаты используются как совместимый baseline и перенесены в таблицы `legacy_stats`/`legacy_daily_stats`. Доступные исторические образцы импортируются с признаком `legacy=1`; исходные JSON не удаляются.
- Все штатные runtime-state модули (manual QA, очереди, bad answers, recent replies, bot stats, feedback, fixes, контекст, moderation, admin activity и panel sessions) используют таблицу `bot_state` той же базы. Legacy JSON читается только для одноразовой миграции; новые рабочие записи в JSON не сохраняются.
- Ежедневные резервные копии описаны в `deploy/kobras1botwiki-db-backup.service` и `.timer`: SQLite Online Backup API, integrity check, SHA-256, хранение 14 дней в `.cache/db-backups/`. Deploy сначала пытается установить systemd timer через NOPASSWD sudo, а при ограниченных правах использует пользовательский crontab на 03:30 и создаёт первичный backup.
- `scripts/verify_runtime_storage.py` проверяет integrity, обязательные таблицы и все runtime namespace после старта. `deploy/update-and-restart.sh` перед синхронизацией сохраняет DB/WAL/SHM и legacy-state, допускает только data-only локальное расхождение, мигрирует state и устанавливает backup timer.
- Миграция production выполнена с резервной копией `.cache/migration-backups/20260917-104946`: импортировано 436 пропущенных образцов и 30 образцов ответов. Полный текст всех исторических сообщений восстановить нельзя, если его не было в логах или экспорте, поэтому агрегаты не превращаются в выдуманные сообщения.
- Для группы `-1002295062981` за 2026-09-16 сохранён точный baseline: 383 входящих сообщения и 1 ответ.
- `app/bot/topic_classifier.py` отправляет доступные сообщения дня в LiteRouter, группирует их в темы, проверяет индексы исходных сообщений и сохраняет результат в `daily_topics`. Ограничение `max_tokens` отключено при `LITEROUTER_MAX_TOKENS=0`.
- Перед ночной тематизацией бот один раз получает `GET /models`, пересекает список с встроенным рейтингом бесплатных моделей и пробует доступные модели последовательно; при сбое discovery используется `LITEROUTER_MODELS`.
- Обычный обработчик сначала просит бесплатные модели из общего `TOPIC_MODEL_PRIORITY` классифицировать сообщение как `QUESTION`/`NOT_QUESTION`; при `NOT_QUESTION` бот молчит. После `QUESTION` он ищет статью в индексе вики и дополнительно проверяет AI её содержательную релевантность, чтобы совпадение только по модели не стало ложным ответом. При отсутствии подтверждённого результата `app/bot/context_ai.py` передаёт до 50 предыдущих сообщений той же пары `chat_id` + `topic_id`; текущий вопрос из истории исключается. При ошибке или некорректном ответе используется следующая модель; если весь список не дал завершённый ответ, вопрос остаётся в обычной очереди пропусков.
- AI также формирует темы и их группировку. Итоговое сообщение статистики собирается кодом из SQLite, количества сообщений, сохранённых тем и шаблонных вступительной/финальной фраз; полный текст сводки AI по-прежнему не генерирует.
- Тест на данных 16 сентября сохранил 3 темы: Orca Slicer/профили/прайм-башня — 17 сообщений; трубка в сопле/засор термобарьера — 11; поддержка и замена деталей — 4. Модель: `deepseek-v4-flash:free`.
- Production после изменений: коммит `1b838fa`, health endpoint отвечает, сервис активен под `anycubicwikibot`, локальный `master` и `origin/master` синхронизированы.
- Проверки: миграционные и AI-тесты прошли (`98 passed`, затем `20 passed` для LiteRouter/классификатора), Ruff и `git diff --check` без ошибок.

## Production и деплой

- Серверный SSH-алиас — `kobras1bot`, рабочий каталог — `/home/anycubicwikibot/KobraS1BotWiki`; сервис запускается только пользователем `anycubicwikibot`.
- Безопасный порядок обновления: локальный `git pull` перед push, затем push; на сервере `git pull --ff-only` от `anycubicwikibot`; после этого `sudo systemctl restart kobras1botwiki.service` и проверка `/health`.
- Перед server pull нельзя сбрасывать или перезаписывать неизвестные изменения: live-бот может коммитить data-файлы. Сначала сохранить/проверить их происхождение и только затем синхронизировать ветку.

## Windows-совместимость тестов

- Тесты должны работать на Windows и Linux.
- POSIX-only модули (`fcntl`, `termios`, `pwd`) нельзя импортировать без проверки доступности. Cleanup обязан работать без POSIX API.
- Для проверки живого PID на Windows нельзя использовать `os.kill(pid, 0)`; production-код использует `psutil.pid_exists()`, POSIX-ветка сохраняет `os.kill`.
- Конкурентная замена общего файла на Windows выполняется под внутрипроцессной блокировкой с ограниченным retry для временного `PermissionError`.
- Проверки порядка обработчиков не должны зависеть от фиксированных индексов, если в список могут добавляться новые handlers.
- Подробное правило: `.codex/windows-test-compatibility.md`.

## Зафиксированная диагностика 2026-09-14

- Перезапуски Codex во время тестов были вызваны Windows-несовместимыми сценариями lock/cleanup и конкурентной atomic-записью, а не общей неисправностью Python.
- После исправлений на Windows успешно прошли полный pytest (`913 passed`), Ruff, pytest с coverage (`64%`) и параллельный запуск pytest/Ruff через `Promise.all` с коротким начальным polling.
- Длинные локальные проверки запускать из отдельного терминала, без параллельных задач Codex; полный прогон по умолчанию предпочтительно выполнять в CI.
