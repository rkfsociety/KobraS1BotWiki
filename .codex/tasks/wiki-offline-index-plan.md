# План: локальная база статей с обновлением без обязательного sitemap

Статус: план реализации, код обхода ещё не реализован.
Дата: 2026-09-28.
Задача: сохранить работоспособность поиска при отказе sitemap Anycubic и обновлять базу обходом ссылок с https://wiki.anycubic.com/en/home.

## Результат и границы

Бот отвечает из последней успешно сохранённой локальной базы. Фоновый обход получает текст статей и новые ссылки одним запросом. Сбой сети, sitemap или отдельной статьи не стирает рабочую базу и не задерживает запуск Telegram-бота.

Область первой версии — публичные HTML-статьи английского раздела `/en/`. Это база текстов и официальных ссылок, а не полноценное зеркало сайта: картинки, видео, PDF, авторизация и выполнение JavaScript не входят в задачу. Ссылки в ответах продолжают вести на Anycubic; при недоступности всего сайта открыть их нельзя, хотя локальный поиск продолжает работать.

Обход по ссылкам не гарантирует обнаружение страниц без входящих ссылок. Нельзя сообщать «скачан весь сайт» без доказательства полноты. Статус должен различать завершение доступной очереди, отложенные ошибки и достижение лимита.

## Подтверждённые исходные условия

- `app/web_wiki_index.py`: загрузка HTML, извлечение текста, файловый кэш, поисковый индекс и пакетный `WebWikiIndexer.step()` уже существуют. Использовать их и установленные httpx/BeautifulSoup.
- `WebWikiIndex.add_docs()` добавляет документы без замены по URL. Повторное обновление требует удаления дублей и согласованного обновления поисковых структур.
- `app/bot/lifecycle.py::_index_step` выполняет блокирующий шаг через `asyncio.to_thread`, но удаляет job после завершения очереди. Для регулярного обновления нужна сохраняющаяся задача с проверкой срока следующего обхода.
- `app/bot/wiki_reindex.py`: переиндексация всё ещё очищает документы до получения новых текстов. Также вызов `_save_state()` без аргумента не соответствует сигнатуре `_save_state(st)` индексатора; этот путь необходимо исправить и проверить в рамках переработки обновления.
- В текущем дереве есть незакоммиченные правки прошлых шагов: подавление одинаковых ошибок sitemap, резервный `data/sitemap.xml`, перенос получения URL перед очисткой индекса и соответствующие тесты/документация. Это промежуточное решение, не готовый crawler. Перед реализацией сверить diff и сохранить постороннюю работу.
- `data/sitemap.xml` содержит 1816 записей URL, включая повторы; это не число уникальных актуальных статей. Снимок использовать как дополнительный начальный источник, не как свидетельство полноты.
- Проверенная страница `/en/home` отдаёт HTML с обычными ссылками на разделы. Полнота извлечения статей и ссылок из страниц разных типов ещё требует проверки.

## Выбранный подход

### 1. Постоянная база и возобновляемая очередь

Расширить существующий файловый кэш без добавления БД или production-зависимостей. Для каждого нормализованного URL хранить последнюю хорошую статью, извлечённые ссылки, хеш содержимого, HTTP-валидаторы, время успешной проверки, ошибку, число попыток и срок следующей попытки. Очередь и метаданные должны иметь версию формата.

Предпочтительный формат — единый атомарно заменяемый checkpoint с документами, метаданными и состоянием обхода. Два независимо перезаписываемых файла не обеспечивают согласованность очереди и базы при аварии. Старые cache/state импортировать однократно, сохранив исходные файлы для отката; после импорта не поддерживать два источника истины. При проектировании формата проверить существующий лимит размера кэша и стоимость сериализации на реальном объёме.

Порядок публикации пакета: подготовить изменения вне поискового lock → успешно сохранить checkpoint → опубликовать согласованную версию индекса в памяти. При сбое записи активная версия продолжает работать, незаписанные страницы не считаются завершёнными. После аварии допустима повторная загрузка, но повторная обработка URL должна быть идемпотентной. На Windows проверить временный файл в том же каталоге и замену без потери последней хорошей версии.

### 2. Обнаружение адресов

Начальные адреса: `/en/home`, URL из существующей базы, настроенные дополнительные страницы и подходящие адреса резервного sitemap. Приоритет обхода: главная, разделы поддерживаемых принтеров, затем остальные статьи. Не жертвовать текущей базой из-за смены источника адресов.

При успешной загрузке статьи одновременно извлекать текст и ссылки. Использовать `urljoin` для относительных ссылок, удалять фрагменты, исключать повторные URL. Для английских статей query-параметры не создавать как отдельные документы. Не менять регистр пути и не декодировать произвольно значимые символы URL.

Допускать только HTTPS, точный разрешённый hostname и путь `/en/`; проверять каждый переход редиректа до следующего запроса, ограничить число переходов. Исключать вложения по пути и типу ответа. Не доверять внешнему `canonical` или HTML `base` как разрешению покинуть сайт. Ссылки извлекать из содержимого и релевантной навигации, не ограничиваться одной главной страницей.

Sitemap остаётся необязательным способом обнаружения дополнительных адресов. Его отказ не блокирует обход и не вызывает ERROR о неисправности всего бота. Успешный sitemap также валидировать: HTML-страницу ошибки нельзя принять за карту сайта.

### 3. Ограниченный фоновый загрузчик

Расширить `WebWikiIndexer.step()` и существующий планировщик. Не выполнять полный обход в конструкторе, при запуске бота или в обработчике webhook. Команда обновления ставит работу в очередь и возвращает её состояние.

Начальные параметры: один одновременно выполняемый запрос к вики, пауза не менее секунды между запросами, ограничение времени и числа страниц одного шага. Учитывать robots.txt и более строгие ограничения источника. При временной невозможности получить правила повторить позже; существующая база остаётся доступной.

Для 429 учитывать `Retry-After`; для временных HTTP/сетевых ошибок применять ограниченные отложенные повторы с увеличением интервала и небольшим случайным разбросом. Не делать три немедленных запроса подряд. После исчерпания попыток в цикле переносить страницу в следующий цикл; необработанная ошибка не равна успеху.

При массовых сбоях приостанавливать запросы к хосту, затем проверять восстановление одиночным запросом. Это предотвращает тысячи одинаковых ошибок. Ограничивать объём ответа при чтении потока, а не после загрузки всего тела. Клиент и ответы должны закрываться также при отмене и исключениях.

Один владелец изменяет очередь и checkpoint. Плановый обход, ручное обновление и webhook не должны создавать параллельные загрузчики или конфликтовать с публикацией индекса.

### 4. Обновление без потери знаний

Новый проверенный текст заменяет документ с тем же URL; новая статья добавляется. При публикации обновлять все производные структуры поиска, включая кэш результатов и индекс кодов ошибок.

При таймауте, 500, 403, странице входа, CAPTCHA или некорректном HTML сохранять старый текст и отмечать неудачную попытку. Проверять структуру страницы и наличие содержимого; не принимать HTTP 200 автоматически за статью и не отбрасывать корректные короткие статьи одним порогом длины.

В первой версии не удалять документы автоматически из-за пропавшей ссылки или одиночного 404/410. Повторно недоступные статьи отмечать в состоянии, сохраняя возможность разбирательства. Политику окончательного удаления выделить в последующую задачу.

`ETag`/`Last-Modified` использовать при наличии. На 304 сохранять текст и ранее извлечённые ссылки. Если локального содержимого для такого ответа нет, повторить запрос без валидаторов. Хешировать полезный текст и набор ссылок отдельно, чтобы изменение навигации не терялось из-за неизменности текста.

### 5. Периодичность, лимиты и наблюдаемость

Первый обход запускается фоном сразу после загрузки существующей базы. Далее — цикл обновления примерно раз в сутки, с распределением запросов во времени. Если цикл ещё идёт, новый не создавать. Новые найденные ссылки обрабатывать в текущем цикле, ошибки — по собственному сроку повтора.

Начать с текущего `WIKI_MAX_PAGES`, уточнив его семантику как лимита уникальных статей. При достижении лимита не удалять ранее сохранённые документы и явно отмечать неполное покрытие. Дополнительно ограничить размер очереди и дискового checkpoint; определить значения после измерения пробного обхода. Полный запуск не объявлять успешным при молча отброшенной очереди.

Расширить существующий статус: доступные документы, очередь, отложенные ошибки, время последней успешной загрузки и завершённого цикла, источник обнаружения, признак ограничения охвата. Не требовать новой панели для первой версии.

В Telegram отправлять переходы состояния: массовый сбой, восстановление, завершение первого наполнения или достижение лимита. Подробности отдельных страниц оставлять в локальном журнале с ограничением повторов. Исправный обход при неработающем sitemap считается рабочим режимом.

## Порядок реализации и доказательства

1. **Защита текущей базы и формат состояния.** Изучить фактический production-кэш read-only перед миграцией, проверить стоимость выбранного формата. Добавить импорт старого кэша без сброса документов и согласованное сохранение checkpoint. Проверить сбой записи, перезапуск и повторную обработку без дублей.
2. **Извлечение и очередь ссылок.** Добавить нормализацию URL и извлечение ссылок в существующий шаг загрузки. Проверить относительные ссылки, циклы, фрагменты, внешние ссылки, редиректы, вложения и лимиты на небольших HTML-фикстурах.
3. **Обновление статей.** Реализовать замену документа по URL и сохранение старой версии при сбое; проверить также поиск по коду ошибки после обновления и 304 с/без локального текста.
4. **Расписание и управление.** Переработать жизненный цикл job, ручную переиндексацию и webhook. Проверить отсутствие параллельных обходов, задержки запуска Telegram и потери очереди после рестарта; исправить связанный вызов `_save_state`.
5. **Живой пробный обход.** Небольшой ограниченный запуск от раздела Kobra S1 в отдельный временный кэш. Проверить ссылки, извлечённый текст, отсутствие шаблонов ошибок в индексе и поиск по нескольким реальным вопросам. Измерить скорость, объём и память; не подменять этим проверку полного охвата.
6. **Проверки и документация.** Целевые pytest/Ruff локально, полный набор через существующий CI. Windows и Linux: сохранение/замена файлов, отмена работы и возобновление. Обновить архитектуру и эксплуатационную документацию, пересмотреть промежуточные правки текущего diff. Статический резервный sitemap не должен оставаться единственным механизмом работы при отказе live sitemap.
7. **Production после разрешения пользователя.** Сохранить рабочий кэш и состояние, синхронизировать изменения без потери серверных данных, развернуть и проверить сервис/health/количество документов. Первый обход выполнять фоном с наблюдением за нагрузкой и ошибками. Для отката сохранить старый формат кэша вместе с предыдущей версией приложения.

## Критерии приёмки

- При недоступном sitemap и доступных статьях база пополняется обходом ссылок.
- При полном отказе Anycubic локальный поиск работает, данные сохраняются, повторные запросы ограничены.
- Изменённая статья обновляется без дублей; новая связанная статья обнаруживается.
- Перезапуск продолжает очередь, а авария записи не повреждает последнюю опубликованную базу.
- Запуск и обработка Telegram-сообщений не ждут завершения обхода.
- Ошибочная HTML-страница не заменяет хорошую статью.
- Достигнутый лимит и отложенные ошибки видимы; они не выдаются за полное завершение.
- В логах нет ежечасного потока одинаковых сообщений об отказе необязательного sitemap.

## Текущее состояние задачи

План записан; реализация этого плана, полный обход и production-деплой не выполнены. Прежние локальные проверки относятся только к промежуточным правкам, не доказывают работу описанной системы. После реализации удалить этот временный план, сохранив действующее поведение в канонической документации проекта.
